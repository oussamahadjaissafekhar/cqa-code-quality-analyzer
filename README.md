# CQA — Code Quality Analyzer

[![CI](https://github.com/oussamahadjaissafekhar/cqa-code-quality-analyzer/actions/workflows/ci.yml/badge.svg)](https://github.com/oussamahadjaissafekhar/cqa-code-quality-analyzer/actions/workflows/ci.yml)
[![Quality gate](https://github.com/oussamahadjaissafekhar/cqa-code-quality-analyzer/actions/workflows/quality.yml/badge.svg)](https://github.com/oussamahadjaissafekhar/cqa-code-quality-analyzer/actions/workflows/quality.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](https://opensource.org/licenses/MIT)
[![Python 3.10+](https://img.shields.io/badge/python-3.10%2B-blue.svg)](https://www.python.org/downloads/)

`cqa` is a static analysis CLI for Python, TypeScript, and JavaScript. It turns
source code into a schema-stable JSON result, a SARIF file for GitHub code
scanning, or a human-readable table/Markdown report.

The design keeps responsibilities separate:

* **Python** owns configuration, file discovery, rules, scoring, reporting, CI
  adapters, and exit codes.
* **TypeScript** owns syntax facts only (`packages/parser-core`). It never emits
  findings, scores, or verdicts.
* A pure-Python AST/heuristic fallback keeps the CLI usable without Node.

The JSON contracts live in `contracts/` and are mirrored by pydantic models
(`src/cqa/models.py`) and TypeScript types (`packages/shared`).

## Requirements

* Python 3.10+
* Node.js 20+ and npm (for the TypeScript parser)
* Optional: Docker 24+ for the container image

## Install from a checkout

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
source .venv/bin/activate

pip install -e ".[dev]"
npm ci
npm run build
```

The parser is resolved from `packages/parser-cli/dist/main.js`, the `outDir`
configured in `packages/parser-cli/tsconfig.json`. If Node or the built parser
is unavailable, `cqa` logs a warning and uses the Python fallback.

After installation the `cqa` script is on `PATH`. On Windows, `python -m cqa`
works without activating the virtualenv:

```powershell
$env:PYTHONPATH = "src"
python -m cqa --help
```

## Quick start

```bash
# Write a starter cqa.toml in the current directory.
cqa init

# Human-readable report (TTY only; non-TTY falls back to JSON).
cqa analyze . --format table --fail-on high

# Machine outputs for CI: canonical JSON plus an extra SARIF file.
cqa analyze . --format json -o cqa-results.json --sarif cqa.sarif

# List every rule with its effective severity.
cqa rules --format table

# Tool, schema, and parser versions.
cqa version --format json
```

Analyze a single file or a subdirectory the same way:

```bash
cqa analyze src/ --format table
cqa analyze path/to/file.py --format json
```

## Configuration

`cqa` looks for `cqa.toml`, `.cqa.toml`, or `[tool.cqa]` in `pyproject.toml`.
A starter file is generated by `cqa init`:

```toml
schema_version = 1

[discover]
include = ["**/*.{py,ts,tsx,js,jsx}"]
exclude = ["**/node_modules/**", "**/.git/**", "**/dist/**"]
use_gitignore = true

[parser]
languages = ["python", "typescript", "javascript"]
timeout_s = 120
jobs = 0

[rules]
disable = []
# overrides = { "secrets.hardcoded" = { severity = "medium" } }

[thresholds]
fail_on = "high"
# max_high = 0

[report]
formats = ["json"]
sarif = false
```

Configuration precedence is **CLI flags > environment variables > config file >
defaults**. Unknown keys fail closed.

### Useful environment variables

| Variable | Maps to |
| --- | --- |
| `CQA_CONFIG` | `--config` |
| `CQA_FAIL_ON` | `--fail-on` |
| `CQA_FORMAT` | `--format` |
| `CQA_PARSER_BIN` | `--parser-bin` |
| `CQA_PARSER_VERSION` | reported parser version override |
| `NO_COLOR` | disables ANSI color |

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success; no findings at/above the fail threshold |
| `1` | Findings at/above the fail threshold (quality gate) |
| `2` | Invalid arguments or configuration |
| `3` | Path, permission, or write failure |
| `4` | Parser subprocess failure |
| `5` | Parser or run timeout |
| `130` | Interrupted (`Ctrl+C`) |

Treat `1` as a quality gate failure and `2–5` as infrastructure failures.

## Baseline and incremental runs

Accept existing findings once, then fail only on new ones:

```bash
cqa analyze . --baseline cqa-baseline.json --update-baseline
cqa analyze . --baseline cqa-baseline.json
```

For CI change sets, pipe a NUL-separated path list:

```bash
git diff --name-only -z origin/main...HEAD | cqa analyze --stdin-files --format github
```

## Reports

| Format | Use |
| --- | --- |
| `json` | Canonical `analysis-result.schema.json` output |
| `sarif` | SARIF 2.1.0 for GitHub code scanning |
| `markdown` | GitHub Step Summary friendly |
| `github` | `::error` / `::warning` / `::notice` workflow commands |
| `table` | Aligned columns; TTY only (falls back to JSON) |

`--sarif PATH` writes SARIF in addition to the selected `--format`. When running
inside GitHub Actions, a Markdown step summary is appended automatically.

## Architecture

```text
CLI (click) ──> app.run_analyze ──> discovery ──> parser bridge ──> rules ──> reports
                                      │                │
                                 .gitignore       Node parser or
                                 globs, limits    Python fallback
```

```text
src/cqa/                 Python CLI
  app.py                 analysis pipeline (no Click, no rendering)
  cli.py                 option parsing + exit-code mapping only
  config.py              load/merge/validate TOML
  fs/discover.py         gitignore-aware traversal
  parsers/               Node bridge + Python fallback
  security/              rule engine and rule packs
  quality/               complexity metrics and thresholds
  report/                JSON, SARIF, Markdown, GitHub, table renderers
  ci/                    GitHub context and artifact writers
packages/                TypeScript syntax-fact parsers
contracts/               JSON Schema (v1, additive-only)
tests/python, tests/ts   pytest and Jest suites
```

Parsers receive file content in the JSON request and return facts plus per-file
errors. A failure in one file never aborts the batch.

## Docker

The repository-root `Dockerfile` builds a small, non-root runtime image in
three stages:

1. **`node-build`** compiles the TypeScript parser (`npm ci && npm run build`)
   with a BuildKit npm cache mount.
2. **`python-build`** installs the CLI and its dependencies into a
   self-contained virtualenv with a pip cache mount.
3. **`runtime`** copies only the virtualenv, the compiled `@cqa/*` packages, and
   the Node binary from `node:20-bookworm-slim`. No npm, compilers, tests, or
   build caches are shipped.

Build and run:

```bash
docker build -t cqa:local .
docker run --rm -v "$PWD:/workspace" -w /workspace \
  cqa:local analyze src --format table
```

On Linux, if your UID is not `1000`, add
`--user "$(id -u):$(id -g)" -e HOME=/tmp` so the container can write its cache
and `-o` reports into the bind mount.

`make docker` is a shortcut for the build. The container:

* runs as non-root UID/GID `1000`;
* expects the project at `/workspace` and uses it as the working directory;
* forwards arguments straight to `cqa` (`cqa:local analyze ...`);
* sets `CQA_PARSER_BIN=/opt/cqa/parser-cli.js`;
* accepts `--user "$(id -u):$(id -g)"` for host-owned bind mounts.

Local parity through Compose:

```bash
docker compose -f docker/docker-compose.yml build
docker compose -f docker/docker-compose.yml run --rm cqa analyze src --format table
```

## CI/CD pipeline

| Workflow | Trigger | Purpose |
| --- | --- | --- |
| `.github/workflows/ci.yml` | push to `main`, pull request | TypeScript build/typecheck/tests, Python lint/typecheck/tests, Docker smoke test, composite-action smoke test |
| `.github/workflows/quality.yml` | pull request, push to `main`, manual | Build the image, run the quality gate on production sources, publish SARIF and artifacts |

### Quality gate (`quality.yml`)

1. Builds the image with Buildx and GitHub Actions layer caching.
2. Smoke-tests the image with `cqa version --format json`.
3. Runs `cqa analyze` on `src` and `packages` with `--fail-on high`, writing
   `cqa-reports/<tree>.json` and `cqa-reports/<tree>.sarif`.
4. Appends a Markdown summary to the job page and uploads the `cqa-reports`
   artifact even when the gate fails.
5. Exits with code `1` when either analysis run reports findings at or above
   `high`.

Exit codes are interpreted as documented above: `0` passes, `1` is a
quality-gate failure, and `2–5` abort the job as infrastructure errors so they
are fixed rather than mistaken for accepted findings.

The gate analyzes `src` and `packages` rather than `.` because the repository's
test fixtures intentionally contain vulnerable patterns and fake secrets.
Analyzing the whole checkout would fail on fixture data that never ships. Add
paths to the loop in `quality.yml` (or provide an `--exclude`/baseline config)
when new production trees are introduced.

### Blocking merges

A green workflow is not enough on its own. In the repository settings, add a
branch protection rule for `main` and mark the `quality` job (shown as
**Quality gate / quality**) as a **required status check**. Once required:

* a failing gate blocks the merge button until the findings are fixed or the
  threshold/baseline is deliberately changed;
* skipped or cancelled runs keep the check from passing;
* cost is bounded by a 25-minute job timeout and concurrency cancellation.

SARIF upload is best-effort (`continue-on-error`) because pull requests from
forks may not receive `security-events: write`. The final enforcement step is
authoritative.

Reproduce the gate locally:

```bash
docker build -t cqa:local .
docker run --rm -v "$PWD:/workspace" -w /workspace cqa:local \
  analyze src --format json -o cqa-results.json --sarif cqa.sarif --fail-on high
echo $?   # 0 = pass, 1 = findings at/above high, 2-5 = infrastructure
```

The reusable composite action in `.github/actions/cqa` wraps the same container
run for single-path jobs; see `.github/ACTION.md` for its full input/output
matrix.
